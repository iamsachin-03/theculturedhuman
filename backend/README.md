# Backend for family archives and the marketplace

The family archive app at `/app.html` stores each person's archive in a [Supabase](https://supabase.com) project: Postgres for the data, Supabase Auth for sign-in, and Supabase Storage for voice notes, videos, photographs and documents. The browser talks to it directly with the public anon key; row-level security in the database decides what each person can see. Until a project is connected, the app runs in preview mode, keeping everything in the visitor's browser.

The few things that need a server (payments, the daily emails, the weekly WhatsApp question and link previews) are Python functions in `api/`, run by Vercel. They use the standard library only, share `web.py` for HTTP, the database and the cron secret, and are tested with `npm run test:py`. Locally, `npm run serve` runs them through `tools/run_function.py`, so you need Python 3.10 or newer.

| File | What it is |
| --- | --- |
| `schema.sql` | Tables, row-level security rules, the functions behind sharing and passing an archive on, and the storage bucket rules |
| `places.sql` | The places from `content/places/*.json`, ready to insert. Generated by `npm run build`; run it again when a place is added |
| `test.sql` | 89 checks of the access rules: strangers, family, beloved ones, letters with dates, legacy contacts, silence, deleting an account, moderation, reports, daily limits, bookings, contacts and echoes |
| `test.sh` | Runs `test.sql` against a throwaway local database |
| `web.py` | What every Python function shares: outgoing HTTP, the Supabase REST helper, the constant-time cron secret check and the WSGI adapter |
| `payments/razorpay.py` | Online payment for accepted quotes: orders, Checkout signatures and the webhook. Run by `api/razorpay-order.py` and `api/razorpay-webhook.py` |
| `notify/notifier.py` | The daily emails: what you shared was published (or why not), and each step of a booking. Run by `api/notify.py` |
| `share/preview.py` | The link preview for a shared contribution at `/s/<id>`. Run by `api/shared.py` |
| `weekly/` | The optional WhatsApp sender for the weekly question ([its README](weekly/README.md)) |
| `dev/start.sh`, `dev/dev-server.mjs` | A local stand-in for a Supabase project, for development and tests only |

## What the rules guarantee

These mirror `public/scripts/app-core.js`, which the app uses to explain the same rules on screen. Keep the two in step.

- **Every archive belongs to one person.** Only the owner and the person who added an entry can change or delete it.
- **Sharing is per entry.** Each entry has an audience: only me, my family, specific people, specific people from a date, or when my archive is passed on.
- **People are added by email.** An owner adds someone as family who can add, family who can view, a beloved one, or a legacy contact. When that person signs in with the email address, `claim_people()` links them. Changing the email address unlinks them.
- **"Only me" stays private forever,** even after an archive is passed on, and entries with a date stay hidden until that date.
- **Relatives cannot hold things back.** Family who can add may add entries to someone else's archive, but only for "only me and the owner" or "the family".
- **Passing an archive on is slow and cancellable.** A legacy contact reports a death with `report_passing()`. The archive is passed on when the waiting period ends (30 days by default), unless the owner signs in first (`touch_seen()`, called on every visit). If the owner is silent for the quiet period (12 months by default), the daily job `legacy_tick()` moves the archive to "checking" (send reminders), then 30 days later to "asking" (ask the legacy contacts). Browsers cannot call `legacy_tick()`.
- **Files follow their entry.** A file can only be read by people who can see its entry, and only uploaded or deleted by people who can edit it.
- **Leaving is complete.** `delete_my_account()` deletes the account, its archive, and what the person added to other archives. The app removes their stored files first.
- **Place contributions and listings are moderated.** Whatever a browser sends, they start as `pending` and only people in `moderators` can publish them. Editing a contribution sends it back to `pending`; its author can delete it at any time. A moderator's `review_note` (why it was not published, or was taken down) is shown only to the author. Every contribution needs `consent`, and one person can share at most ten a day.
- **Reports reach moderators only.** Signed-in visitors can report a published contribution once, with a reason. The person reported never sees who reported them.
- **Bookings keep money honest.** A booking moves requested, quoted, accepted, paid, completed (or cancelled before it is paid). Only the maker, host or storyteller quotes, and only the family accepts. The database sets the platform fee from the price with `platform_fee()`, which must match `platformFeePercent` in `content/site.json`. Only the payment functions (service key) or a moderator can mark a booking paid or completed, or attach a payment order.
- **Contact details stay private until a quote is accepted.** `booking_contacts()` gives each side the other's email only once the family accepts; moderators see both. The `contacts` table itself is never readable.
- **Echoes are counted, not listed.** "We have this too" rows are visible only to the person who added them; visitors read counts from `contribution_echo_counts`.

## Connecting a Supabase project

1. Create a project (choose the Mumbai region for users in India).
2. In the SQL editor, run `schema.sql`. It also creates the private `archive` storage bucket and its rules.
3. Under Authentication, set the Site URL to the site's address and add `https://<your-site>/app.html` to the redirect URLs. Email sign-in links work out of the box; set up your own SMTP sender before launch, because Supabase's built-in sender is rate-limited. To offer Google, enable the Google provider and set `"google": true` below.
4. Under Storage, set the file size limit you want (the app warns above 50 MB).
5. Schedule `select legacy_tick();` daily with the `pg_cron` extension, and send the reminders for archives that have just moved to `checking` or `asking` (an Edge Function or any email service).
6. Run `places.sql` so families can add to each place, then make yourself a moderator: sign in to the app once, and run `insert into moderators select id from auth.users where email = 'you@example.org';`. Moderators read what families send at `/app.html#/moderate` and publish it to the place page, where it appears straight away. Run `places.sql` again whenever you add a place. The same page lists makers, hosts and storytellers waiting to be published, and accepted bookings: send the family a payment link for the total, then record the payment reference there, and mark the booking completed when the work is done.
7. Put the project URL and the public anon key in `content/site.json` under `backend`, then rebuild:

   ```json
   "backend": { "provider": "supabase", "url": "https://<project>.supabase.co", "anonKey": "<anon key>", "google": false }
   ```

   The anon key is safe to publish; the access rules protect the data. Never put the service role key in the site.
8. For the daily emails, create a [Resend](https://resend.com) account, verify the site's domain, and set these in the Vercel project: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `EMAIL_FROM` (for example `The Cultured Human <hello@your-domain>`), `SITE_URL` and `CRON_SECRET`. The cron in `vercel.json` calls `/api/notify` once a day; open `/api/notify?dry=1` with the secret to see what it would send. Each email is sent once, and only for rows from the last 14 days.
9. For online payments, create a [Razorpay](https://razorpay.com) account and set `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` in Vercel (start with the `rzp_test_` keys; no real money moves). In the Razorpay dashboard, add a webhook to `https://<your-site>/api/razorpay-webhook` for the events `order.paid` and `payment.captured`, with the same secret. Families then see "Pay securely" on an accepted quote (`api/razorpay-order.py` creates the order for the price plus the fee and checks Checkout's signature; the webhook confirms it independently). Without the keys nothing is charged and the moderator sends a payment link as before. To pay makers automatically, look at Razorpay Route later.

## Keeping it locked down

The code already does its part: every table has row-level security (tested by `test.sh`), privileged functions pin their `search_path`, the site sends a strict content security policy, payment and cron requests are checked against their secrets in constant time, and invite links are cleaned before they are drawn. These settings live outside the code, so check them when you connect the project:

- **Redirect URLs.** Under Authentication → URL Configuration, list only the real site (`https://<your-site>/app.html`). A wildcard there lets a sign-in link send its token to someone else's address.
- **Sign-up abuse.** Under Authentication → Rate Limits, keep email sends low (a few per hour per address) and turn on CAPTCHA under Attack Protection before launch.
- **Secrets.** The service role key, `CRON_SECRET`, `RESEND_API_KEY` and the Razorpay secrets belong in Vercel's environment settings only, never in `content/site.json`, the repository or a chat. Make `CRON_SECRET` long and random (`openssl rand -hex 32`), and rotate any key that has been pasted somewhere it should not be.
- **A new project URL.** The content security policy in `vercel.json` names the Supabase project. If you move to another project, change it there too; the site tests fail until you do.
- **Accounts.** Turn on two-factor sign-in for the Supabase, Vercel, GitHub, Resend and Razorpay accounts. Whoever controls those controls the families' archives.
- **Previews.** A tunnel (`cloudflared`, `localhost.run`) makes your local preview public to anyone with the address. Close it when you are done, and never point one at the local stand-in on port 54321.

## Running the tests

With Postgres 15 or later installed locally:

```bash
backend/test.sh                        # if your user can create databases
PSQL="sudo -u postgres psql" backend/test.sh
```

## A local Supabase stand-in

`dev/start.sh` starts a fresh database with `schema.sql`, Supabase Auth ([GoTrue](https://github.com/supabase/auth) binary), [PostgREST](https://postgrest.org) and `dev/dev-server.mjs`, all on `http://localhost:54321` like a Supabase project. The dev server stores files on disk with the same storage URLs as Supabase and the same access rules, and catches sign-in emails so links can be read at `http://localhost:54321/dev/mail`. Because those links sign anyone in, it listens on this computer only and answers only pages on `localhost`. It needs no Docker:

```bash
AUTH_BIN=/path/to/auth PGRST_BIN=/path/to/postgrest PSQL="sudo -u postgres psql" backend/dev/start.sh
```

It prints an anon key and saves it to `/tmp/tch-anon-key`, and saves a service-role key to `/tmp/tch-service-key`. Then:

- run the app against it by pasting this into the browser console on the local site (the override only works on `localhost` or `127.0.0.1`, and only for a backend there): `localStorage.setItem('tch-backend', JSON.stringify({ url: 'http://localhost:54321', anonKey: '<anon key>' }))` (remove the item to go back to preview mode);
- run the app's Supabase integration test: `TCH_DEV_BACKEND=http://localhost:54321 TCH_DEV_ANON_KEY=$(cat /tmp/tch-anon-key) npm test`;
- run the payments test end to end (a real sign-in, an order, a signed webhook marking the booking paid): `TCH_DEV_BACKEND=http://localhost:54321 TCH_DEV_ANON_KEY=$(cat /tmp/tch-anon-key) TCH_DEV_SERVICE_KEY=$(cat /tmp/tch-service-key) npm run test:py`. The service key is saved by `start.sh` and, like Supabase's, bypasses the access rules, so keep it local.
